WI-FI NETWORK TAP -> PASSWORD KEYBOARD PAGE (PAGE 60) FIX (2026-10-30)
- Fixed issue where tapping an available Wi-Fi network row on Page 57 (`WI-FI`) failed to
  open the Wi-Fi Password keyboard (`Page 60`):
  1. Heap Fragmentation / MemoryError Prevention:
     - `dwin_wifi_ui._buf` was lazily allocated (`bytearray(6600)`) inside `_draw()` when
       the user first tapped a Wi-Fi row, while `dwin_get_data._draw_wifi_dots()` allocated
       a new 6600-byte buffer on every redraw. After idle polling fragmented the MicroPython
       heap, `_draw()` raised `MemoryError` on line 90 of `_open_keyboard()` before line 91
       (`_dw().dwin_page(PAGE_KB[0])`) could switch the display to Page 60.
     - Pre-allocated `_buf = bytearray(6 * 1100)` at module import in `dwin_wifi_ui.py` and
       `_wifi_buf = bytearray(6 * _WIFI_DOTS_MAX)` in `dwin_get_data.py` (reused across
       `_draw_wifi_dots()`, `_draw_settings_graphic()`, and `draw_iot_page()`), and added
       `gc.collect()` before drawing and in `dwin_get_data.refresh()`.
  2. Immediate Page Switch & State Update in `_open_keyboard()`:
     - `_open_keyboard(row)` now calls `_dw().dwin_page(PAGE_KB[0])` and sets `_page = PAGE_KB[0]`
       before `_draw()`, ensuring instant page transition and `dwin_wifi_ui.busy() == True`
       on the same loop iteration.
  3. Always-Synced `wifi_rows` & Scan Fallback:
     - `dwin_get_data._draw_wifi_dots()` now updates `wifi_rows` at the top of the function
       (before any early return) and falls back to `top_ssid` / `ssid` when `scan` is not yet
       populated.
     - `dwin_wifi_ui._rows()` falls back to `iot_bus.status().get("scan")` and `top_ssid`/`ssid`
       if `dwin_get_data.wifi_rows` is empty, and `poll()` forces `_draw_wifi_dots(force=True)`
       on entering Page 57 if `wifi_rows` is empty.
     - Tapping `SCAN` (`0x0110`) immediately sends `IOT:{"id":50,"op":"wifi_scan"}` to ESP32.
- Synced `board_r4/dwin_wifi_ui.py` and `board_r4/dwin_get_data.py` to `board_main/` and
  installed to STM32H723 (`COM88`).

DWIN NO-REPLY / BLIND MODE & DISPLAY WIRING DIAGNOSIS (2026-10-26)
- Root Cause Identified:
  1. The board diagnostics showed:
     `dwin: no reply from the display (its TX does not reach PD8) - sending without checks`
  2. In `dwin_screen.py` and `dwin_wifi_ui.py`:
     When `_dw_send()` received no ACK at boot, it permanently set `_dw_blind = True`.
     When `_dw_blind` was True, `_dw_read()` returned None immediately and `dwin_wifi_ui.poll()`
     returned at line 228 without doing anything.
  3. Consequently:
     - Tapping "PORT & PIN MANAGER" on the display changes the page internally on the DWIN screen to Page 74.
     - But because the DWIN TX wire did not reach STM32 RX (`PD8`/`PD9`), the STM32 could not read
       current page (`_dw_read(0x0014, 1)` returned None), so `dwin_port_test.poll()` was never invoked!
     - In `lib._telemetry_draw()`: when `page is None`, it called `dw._dw_read(0x0014, 1)`, got None,
       and returned False without drawing any sensor cards!
- Solutions Implemented:
  1. Updated `lib._telemetry_draw()` in `lib.py` (and `lib.mpy`): if `dw._dw_read()` returns None,
     it defaults `page = 40` and proceeds to draw the sensor telemetry cards to VP 0x5500 anyway!
  2. Updated `dwin_screen.py`: removed the `if _dw_blind: return None` lockout in `_dw_read()`. It now
     attempts to read over UART3 and dynamically clears `_dw_blind = False` as soon as replies arrive.
  3. Updated `dwin_wifi_ui.py`: removed `if dw._dw_blind: return`, allowing continuous page polling.
  4. Updated `main.py`: fixed `RX error:` logging.
- DWIN Display Cable Wiring (Motherboard R4 Connector J5):
  * DWIN Pin 1 (5V)  -> Board +5V rail (MOD1 pin 5 or MOD4 pin 5; J5 pin 6 is only 3.3V)
  * DWIN Pin 5 (GND) -> J5 Pin 1 (GND)
  * DWIN Pin 4 (RX)  -> J5 Pin 2 (TXD_DISP - PD8 through R42)
  * DWIN Pin 3 (TX)  -> J5 Pin 5 (RXD_DISP - PD9 through R41)
  Note: If TX/RX are crossed, swap J5 Pin 2 and Pin 5.

- Root Cause Identified:
  1. User reported that when connecting with Blockly, the sensor list was not updating or appearing on the display.
  2. Investigation via board diagnostics revealed that the board had raw uncompiled `lib.py` (153,165 bytes).
  3. When background tasks (Wi-Fi status, clock polling, port manager) ran, the 512 KB MicroPython heap experienced normal fragmentation.
  4. When Blockly sent PLAY, `run_engine()` in `main.py` tried to compile `lib.py` from source. The compiler attempted to allocate a contiguous block of 7,352 bytes, which failed with:

  3. Updated `board_r4/main.py` to preload `lib` at board boot right after `iot_bus.set_uart()`, ensuring `sys.modules['lib']` is always active and available to `dwin_wifi_ui.py`.

3.2 main.py protocol (text over USB serial)
  UPLOAD                      erase user.py
  @@START <code> @@END        save <code> as user.py; main.py adds the header
                              "import system_status / from lib import * / import asyncio"
                              and prints ">> Upload complete."
  PLAY                        run user.py (calls main() or start()); prints ">> Executing..."
                              and ">> Ready." when it ends
  STOP                        stop the running program (watcher task raises KeyboardInterrupt;
                              if the program does not stop within 3 s the board resets)
  MAINVER?                    -> "MAINVER:r4.6-video"
  LIBVER?                     -> "LIBVER:" + lib.VERSION (our lib.py has none -> "?")
  @@FILE:lib.mpy:<sha256>\n<base64>@@FILEEND   library update (only lib.mpy allowed)
  SOFT_RESET, HARD_RESET      reset words (the page's reset buttons)
  Commands are only recognised OUTSIDE @@START..@@END, so program text may contain any word.

3.3 What was fixed in main.py (r4 -> r4.6)
  - USB receive had no flow control: big uploads lost bytes ("IndentationError" on the
    board). Now usb.init(flow=USB_VCP.RTS). 28 KB uploads are byte-exact in ~3-5 s.
  - Words like PLAY/STOP/UPLOAD inside the program text (even "DISPLAY") triggered commands.
  - On MicroPython 1.28 an exception raised in a scheduled timer callback is only printed,
    so the old STOP never stopped programs. Now a watcher task in the event loop does it.
  - Errors in the main loop no longer end main.py (Ctrl-C still exits to the prompt).
  - Data is received by a 10 ms soft timer (stop_checker -> _INBOX); only the main loop
    touches BUFFER.
  - r4.5: the uploaded program is never held in memory as a whole (a 29 KB upload used to
    fail with "memory allocation failed" on a fragmented heap). Incoming text goes into one
    fixed 16 KB buffer (allocated at start-up); only the last 4 characters are held back to
    find "@@END". A program up to 16 KB is written to user.py in one go at @@END; a bigger
    one is written 16 KB at a time as it arrives. (r4.4 wrote user.py.new + rename; that
    cost ~5 s extra per upload and was dropped - an interrupted big upload now leaves a
    partial user.py: upload again.)
    After a program ends its module is removed at once (sys.modules.pop("user")), so its
    picture data no longer blocks the next upload.
    Upload time is set by the flash (section 9.13): measured 4.5 s for a tiny program,
    ~14 s for 27-68 KB (earlier, on a freshly formatted flash, 27 KB took 2.4 s).

3.4 lib.py DWIN section (board_main\lib_dwin_section.py)
  Blocks call the async versions; every function also has a plain version.
  dwin_image(img)      draw a picture on page 39 (~10 s; the 115200 baud UART is the limit)
  dwin_clear()         remove it
  dwin_page(n)         switch display page
  dwin_save(slot)      slot 1-3: save the picture on page 39 into the display's own memory
                       AND refresh the PROJECTS LIST pages (~10 s after dwin_image, ~20 s
                       otherwise because the pixels must be read back from the display)
  dwin_show_saved(slot) show a saved picture again (0.13 s, no picture data on the UART)
  img = (width, height, enc, data): RGB565 big-endian pixels, max 160x106,
        enc 1 = zlib-compressed, enc 0 = raw; data = lowercase hex, either one string or
        (what the Blockly "show image" block makes now) a tuple of strings of at most
        4096 characters. One long string literal makes "import user" need one large free
        block (it failed at 37 KB); short pieces do not. The hex is decoded through two
        reusable buffers (compressed data 32 KB, pixels 34 KB), allocated once.
  How a picture is drawn: page 39 has two "Basic Graphic" controls that redraw a list of
  dots from display memory every frame: VP 0x1000 (max 6900 dots) and VP 0x8400 (max
  10560 dots). Each dot = x, y, colour; each picture pixel becomes a 3x3 dot. Frames of
  40 dots, each acknowledged by the display (5A A5 03 82 4F 4B), resent up to 3 times.
  Memory: one reusable 34 KB pixel buffer; the last drawn picture is kept for dwin_save.
  The zlib picture data is decoded by lib.py's own decoder (_dw_inflate, after puff.c)
  straight into that buffer. MicroPython's deflate module is NOT used: it needs a separate
  32 KB window block and failed with MemoryError after a few runs.
  The JPEG encoder (dwin_save) reads the RGB565 pixels directly (no 3 x 17 KB colour
  planes - those failed with MemoryError) and uses the idle compressed-data buffer as its
  8 KB working buffer, so a save allocates no large block.

3.5 How saving works (two places in the display)
  a) Display database (on-chip flash, 160K words): VP command 0x0008 copies VP memory
     <-> database inside the display. Slot = 4-word header "DWIM" + region A (20704
     words) + region B (31684 words). This is what dwin_show_saved() loads (instant).
  b) Picture library 24_SavedPictures.icl in the display's 16 MB flash (font ID 24-25):
     icons 0-2 = thumbnails 120x80, icons 3-5 = large views 408x272, each at a fixed
     32 KB-aligned place. The STM32 makes the JPEGs itself (pure Python encoder in lib.py,
     baseline 4:4:4, standard Huffman tables, quality 85, lowered automatically if a picture
     does not fit) and writes them with VP command 0x00AA (32 KB block writes, staged in
     VP 0x1002 / 0x8402). Icon controls on pages 40-43 show them, so the PROJECTS LIST
     follows every save without an SD card.

3.6 Video (2026-10-21) - short silent clip played by the display itself
  - Blockly: click the picture in the "play video" block (like "show image") and choose
    a video; it is sent to the screen at once (needs the board connected) and the block
    keeps only a 48x32 preview + name/frames/seconds/KB in its saved state (the toolbox
    button of the first version was removed by update_dwin_video_block.py; backup in
    blockly\backups\before_video_block). The browser
    (blockly\dwin_video_src.js, inserted into index.html by add_dwin_video.py) cuts the
    video into 240x160 frames at 10 per second, max 256 frames = 25.6 s (longer videos:
    only the start), encodes them with a JavaScript copy of lib.py's JPEG encoder
    (byte-identical output, tested), quality 75 (lowered to 60/45/30 if > 3.75 MB), and
    builds an icon library: 256 icons; a shorter clip is repeated (repeated icons point to
    the same data). It is sent through main.py's "DWV" transfer to flash font ID 49
    (blocks 392-511), header block last. Speed ~4 s per 32 KB part (a 25 s clip of
    ~2 MB: about 4-5 min; a 5 s clip: under 1 min).
  - Display: page 44 (VIDEO) has an Animation Icon control (record type 0x01: icons
    0-255 of library 49, 5 x 20 ms per frame, loop, opaque) at (120,104); it plays while
    VP 0x5210 = 0 (the value after power-on) and shows icon 0 when it is 1.
    PROJECTS LIST has a VIDEO button in its header (290,9)-(410,39).
  - Board: lib.py dwin_video_play() (VP 0x5210 = 0, page 44) / dwin_video_stop() (= 1),
    blocks "play video" / "stop video".
  - After "stop video" the VP stays 1, so opening VIDEO from the screen shows it paused
    until a "play video" block runs or the display restarts (the touch file only switches
    pages, it does not write the VP).
  - Flashing the SD card again writes the "NO VIDEO YET" placeholder over the uploaded
    video (font ID 49) - upload the video again after every SD flash.
  - main.py "DWV" protocol (r4.6):
      @@DWV:<first block>:<blocks>\n  -> DWV:READY
      <hex of up to 4096 bytes>\n      -> DWV:NEXT    (staged in VP 0x1002+)
      @@DWB:<index>:<crc32>\n          -> DWV:OK i | DWV:ERR i crc   (0x00AA flash write)
      @@DWV:END\n                      -> DWV:DONE n
    30 s without data ends the transfer. The page retries a failed part up to 3 times.

4.6 File formats (decoded from this project's own files)
  .icl    'DGUS_3' + CRC-16/MODBUS of bytes 8.. (little-endian) + length (BE32) + 04 00 +
          last index (LE16) + offsets (BE32 each) + records: w, h, header length, scan
          length + JPEG. JPEGs must be baseline 4:4:4; the scan data must start 4-byte
          aligned (the SOS segment is zero-padded) and the scan is zero-padded to a multiple
          of 4 (icl_tool.dwinify). A wrongly aligned JPEG makes the display hang until it is
          powered off. Page pictures: Pillow quality 90, subsampling=0, optimize=True.
          Pillow cannot decode the padded JPEGs strictly - strip the padding to check them.
  14ShowFile.bin  "\x14DGUS_2", bytes 9-10 = last page (LE); page table at 0x10, 4 bytes per
          page: control count (LE16) + byte offset (BE16); 32-byte control records, byte 1 =
          type (0x00 variable icon, 0x11 text, 0x21 basic graphic), bytes 6-7 = VP.
  13TouchFile.bin 16-byte records: page, x0, y0, x1, y1, target page, FF 00 00 00; ends FF FF.
  Variable icon record: 5A 00 FF FF 00 0A VP x y Vmin Vmax IconMin IconMax Lib Mode 0 0 0 3F 0..
  Animation icon record: 5A 01 FF FF 00 0D VP x y Reset Vstop Vstart IconStop IconStart IconEnd
          Lib Mode Layer IconGamma PicGamma Time(DGUS cycles of 20 ms) Loop(0)/Single(1) Filter
  T5LCFG.CFG 0x0A-0x0B = UART baud divider (baud = 3225600 / value; 0x1C = 115200,
          0x07 = 460800 is the fastest exact standard rate; 921600 is NOT possible).

9. TRAPS AND LESSONS
--------------------
9.1  The board's flash can be wiped. If the board resets while MicroPython writes a file,
     the filesystem may break and MicroPython formats it at the next boot (happened on
     both boards). Keep copies of every board file on the PC; never unplug during writes.
9.2  Do not let a script grab the board's port automatically when the page disconnects:
     on 2026-10-20 that collided with a replug and wiped the board.
9.3  After Ctrl-C ends main.py, the ">>> " prompt appears ~1.5 s later and keys sent in
     that gap are lost. main.py's receive timer keeps running at the prompt and steals
     serial input - stop it (stop_checker.deinit()) before raw-REPL work.
9.4  If PLAY "does nothing", the board is probably sitting at the Python prompt (it echoes
     the command and shows ">>>" or "..."). Soft reset (Ctrl-D) brings main.py back; the
     page now does this by itself.
9.5  The display only accepts SD cards with 4 KB clusters (section 6).
9.6  The display's flash READ command does not work; verify writes another way (4.2).
9.7  JPEG alignment rules (4.6); a bad JPEG hangs the display until power-off.
9.8  Memory on the board (~370 KB free after lib import, ~300 KB during a picture program):
     plenty in total, but big CONTIGUOUS blocks (30 KB+) get hard to find after a few runs.
     Avoid growing strings/buffers and big temporary copies; reuse fixed buffers.
9.13 Writing files on the board's flash is slow and varies: each f.write() call costs
     ~1.5 s plus ~0.2 s per KB (12 KB file: 1 write 4.3 s, 24 writes 40 s). Use few,
     large writes (main.py writes uploads in 16 KB pieces).
9.14 install_file.py checks files in 4 KB pieces; reading a 100 KB file in one go on the
     board fails with MemoryError.
9.9  mpy-cross needs -march=armv7emdp for files with @micropython.native/viper.
9.10 Files LOST in the 2026-10-20 wipe (never backed up, not used by main.py/lib.py):
     the board's own boot.py (1420 bytes), device_id.txt, motor_cfg.json and the folders
     AI_LIB, With_device_id, Without_while, multiple_start_working_code,
     stop_auto_main_execution. Restore them from the company's firmware package.
9.11 Drive letters move: the SD card reader and the board's USB drive swap between E: and
     F:. Check the label (SDCARD vs STM32H743ZI) before writing anything.
9.12 Bash heredocs on this PC mangle backslash escapes in Python code - write such files
     with an editor.
